## 1. Problem and aim
A fest stores ID-card scans in a `HashSet<Student>`. The junior developer's `Student` overrides `equals()` (compares `regNo`) but **not** `hashCode()`. Instead of simply fixing it, I investigate how the `equals()`/`hashCode()` contract affects hash-based collections.

## 2. Background – how `HashSet` finds an element
`HashSet` is a `HashMap` whose keys are the elements. For `add(e)`:
1. compute `h = e.hashCode()` and spread it (`h ^ (h >>> 16)`);
2. pick the bucket `index = (table.length - 1) & h`;
3. in that bucket, an existing entry is a duplicate only if **its stored hash equals `h`** *and* (`same reference` or `e.equals(existing)`);
4. otherwise the element is added.

So `equals()` is consulted **only for elements that have the same hash**. The contract that makes this work is: *if `a.equals(b)` then `a.hashCode() == b.hashCode()`* (and `hashCode()` must stay the same while the fields it uses do not change). Unequal objects may share a hash (a collision), but equal objects must not differ in hash.

### Why the duplicates appear
`equals()` says two scans of the same ID are equal, but `HashSet` never gets to ask: without an overridden `hashCode()` each new object receives a different identity hash. The two "Arun" objects are routed to different buckets (or fail the stored-hash comparison), so `equals()` is not called and both are kept. The contract *equal objects ⇒ equal hash codes* is broken.

### What happens when a field used in `hashCode()` changes after insertion
The entry is stored in the bucket computed from the **old** hash (and with the old hash stored in the node). Afterwards `contains`, `remove` and duplicate detection compute the **new** hash and look in a different bucket, so the element becomes a "ghost": still counted by `size()` and visible during iteration, but impossible to find or remove, and it lets duplicates in. Therefore fields used in `equals()`/`hashCode()` of a hashed key must be **immutable** (`final`), or the object must not be modified while it is in the set.

### How to correct the class and how to verify the correction
Correction: override `hashCode()` using exactly the fields used by `equals()` (here `regNo`) and make `regNo` `final`.
```java
@Override public int hashCode() { return regNo.hashCode(); }   // consistent with equals()
```
Verification (all done in the program): (1) equal objects return equal hash codes; (2) `equals` is symmetric; (3) the set size after the Gate-3 re-scan is 2 (`VERIFICATION` section); (4) the bulk test gives 1,000 for the fixed class; (5) the `Attendance` program prints `Unique students: 2` after TODO 1 (see `Q3_CompleteCode.md`).

## 7. Alternative concept and complexity analysis
The alternatives are `TreeSet<Student>` with `Comparator.comparing(Student::regNo)` and `HashMap<String, Student>` keyed by `regNo`.
```java
Set<Student> byTree = new TreeSet<>(Comparator.comparing(Student::regNo));   // uses compare(), no hashCode needed
Map<String, Student> byId = new HashMap<>();  byId.putIfAbsent(regNo, student);   // key is the String itself
```
Both avoid the junior developer's bug in their own way: the `TreeSet` decides equality **only** by the comparator (so the comparator must be consistent with `equals`), and the `HashMap` uses `String`'s correct `hashCode`/`equals`.

| Structure | Time per scan | Space for n unique students | Measured (400,000 scans, ≈ 98,124 unique) |
|---|---|---|---|
| `HashSet<Student>` | O(1) average, O(n) worst (O(log n) with tree bins) | n entries (~32 B node + ~5 B table slot each) + the Student objects | 77 ns/scan |
| `TreeSet<Student>` (comparator on `regNo`) | **O(log n)** (≈ 17 comparisons for 100,000) | n entries (~40 B node: key, left, right, parent, colour) + Student objects | 695 ns/scan (≈ 9× slower) |
| `HashMap<String, Student>` | O(1) average | same as `HashSet` plus the key reference (the key `String` is shared with the Student) | 168 ns/scan |

The `HashMap` and `HashSet` are the same structure internally (a `HashSet` *is* a `HashMap`), so their difference in this test is mostly JIT/GC noise, not a real algorithmic gap. The `TreeSet` is slower because each scan costs about log₂ n string comparisons and pointer chasing, but it additionally keeps the students **sorted by `regNo`** (useful for an ordered attendance list) and does not depend on `hashCode()`. The `HashMap` is the best choice when the roll should be looked up by ID (`byId.get(regNo)`).

## 8. Conclusion
`equals()` and `hashCode()` are one contract. Hash collections trust `hashCode()` first and only then call `equals()`, so overriding one without the other silently produces duplicates; mutating a key field after insertion breaks lookups even when both methods are correct; and a `TreeSet` follows `compareTo`, so its notion of "same element" must agree with `equals()`.
