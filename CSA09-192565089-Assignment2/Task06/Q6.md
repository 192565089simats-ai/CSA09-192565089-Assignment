## 1. Problem
Emergency patients have severity 1 (critical) to 5 (minor). The doctor must always see the most severe patient next; among equal severities the **earliest arrival** goes first.

## 2. Design (developed without supplied code)
* **Why a plain `Queue` is not enough.** `LinkedList`/`ArrayDeque` queues are FIFO: they serve strictly by arrival. A severity-5 patient who arrived first would be seen before a severity-1 patient who arrived later (shown in the output: *Plain Queue serves …*).
* **PriorityQueue + Comparator.** A `PriorityQueue<Patient>` is a binary min-heap; the head is always the "smallest" element according to the comparator, so `poll()` returns the right patient.
```java
Comparator<Patient> STRICT = Comparator.comparingInt((Patient p) -> p.severity)   // 1 before 5
                                       .thenComparingLong(p -> p.seq);            // then earliest arrival
```
* **Arrival order among equal severities.** `PriorityQueue` is **not stable**: equal elements can come out in any order. The tie is therefore broken explicitly by a unique, increasing **arrival sequence number** (`counter++` at `admit`), so no two patients ever compare as equal and FIFO within a severity level is guaranteed. (A timestamp could repeat; a counter cannot.)
* **Removing the next patient:** `poll()` removes the head and sifts the last element down – O(log n). **Displaying the waiting list:** copy the queue into a list and sort it with the same comparator – O(n log n) – leaving the queue untouched (`waitingList()`).

A heap only guarantees that each parent is ≤ its children, so only the first element is guaranteed to be the smallest. The correct display is a sorted copy, or repeated `poll()`.

        TriageQueue(Comparator<Patient> c) { q = new PriorityQueue<>(c); }
        Patient admit(String n, int sev, long minute) { Patient p = new Patient(n, sev, seq++, minute); q.add(p); return p; }
        Patient next() { return q.poll(); }
        int size() { return q.size(); }
        List<Patient> waitingList() { List<Patient> l = new ArrayList<>(q); l.sort(q.comparator()); return l; }   // O(n log n) snapshot, queue untouched

## 6. Growth investigation
**Prediction (before experimenting).** A binary heap has height ⌊log₂ n⌋. `add` sifts up: O(log n) worst case, O(1) on average for random keys. `poll` sifts down: O(log n) (about 2 log n comparisons). So per-operation cost should grow very slowly – roughly one extra level per doubling – not linearly.

**Measured** (average of 5 runs after warm-ups, ns per operation):
| Queue size n | add (bulk) | poll (drain) | poll + add at steady size n |
|---:|---:|---:|---:|
| 1,000 | 148.3 | 112.6 | 102.6 |
| 10,000 | 36.6 | 169.0 | 150.3 |
| 100,000 | 35.1 | 246.7 | 245.5 |
| 1,000,000 | 83.3 | 333.1 | 433.1 |

**Comparison.** Size grew 1,000× (log₂ n from 10 to 20) while the cost of `poll` grew only ≈ 3× (113 → 333 ns) – consistent with O(log n) plus cache effects at large heaps; `add` stayed small (35–83 ns), matching O(1) average. The 1,000-element `add` figure (148 ns) is warm-up/JIT noise. The prediction is supported.

## 7. Alternative concept and complexity analysis
(a) **Sorted `LinkedList`** – insert each patient at the correct position (walk until the first patient with larger severity) and serve with `removeFirst`. (b) **Array of five FIFO queues** – one `ArrayDeque` per severity; admit appends to queue `s-1`; serve scans levels 1…5 and polls the first non-empty queue.

| Design | Admit | Serve next | Space | Measured admit / next (ns, n = 50,000) |
|---|---|---|---|---|
| `PriorityQueue` | O(log n) | O(log n) | O(n), one array slot per patient | 25.8 / 196.0 |
| Sorted `LinkedList` | **O(n)** (walk) | O(1) | O(n), but a 24-B node per patient | **154,885** / 15.7 |
| Five FIFO queues | O(1) | O(1) (≤ 5 checks) | O(n) + 5 queue headers | 11.2 / 8.0 |

The sorted list becomes unusable as the queue grows (admit cost grew 7.3 µs → 18.7 µs → 154.9 µs for n = 1,000 → 10,000 → 50,000). The **five-queue** design is actually the fastest because there are only five severity levels; its limitation is that it supports only a small, fixed set of levels with no per-patient priority adjustment, whereas the `PriorityQueue` generalises to any comparable key (e.g. an age-adjusted score, needed for the fairness rule below).

## 8. Inquiry – starvation and a fair rule
**Why starvation occurs.** The strict rule always serves the smallest severity number first. If severe cases keep arriving at least as fast as the doctor can treat them, a severity-5 patient is never at the head of the queue. In the experiment one S5 patient arrives at minute 0, a new S1 patient arrives every minute and one patient is served per minute: under the strict rule the S5 patient is **still waiting after 5,000 minutes**.

**Fair rule (aging).** Give every severity level a worth of `W` minutes of waiting: patients are ordered by `arrivalMinute + W × (severity − 1)` (then by sequence number). A patient of severity `s` is therefore served before anyone who arrives more than `W × (s − 1)` minutes after them, i.e. **waiting time is bounded**. Because the key is computed once at arrival, it never changes while in the heap, so the heap stays valid and no re-heapify is needed (the alternative "raise the priority of patients who waited > T" needs removal and re-insertion of each aged patient, O(log n) each, and a periodic scan).
```java
Comparator.comparingLong((Patient p) -> p.minute + (long) W * (p.severity - 1)).thenComparingLong(p -> p.seq)
```
**Results** (W = 30 minutes, i.e. the S5 patient waits at most 120 minutes longer than a newly arriving S1 patient):
| Experiment | Strict rule | Fair rule |
|---|---|---|
| Old S5 patient vs continuous S1 stream | never served (5,000 min) | served at minute **120** |
| Surge stream (20,000 min, mean 1.02 arrivals/min): S1 mean / max wait | 0 / 2 min | 69 / 165 min (W=30); 104 / 209 (W=10) |
| Same stream: S5 mean / max wait | 837 / **1,550** min | 178 / 287 min (W=30); 143 / 247 (W=10) |

**Trade-off (important).** The fair rule bounds the S5 wait but delays critical patients: S1's mean wait rises from 0 to 69 minutes in an overloaded department. For clinical safety `W` must be chosen large enough that S1/S2 patients are never harmed (larger `W` → closer to the strict rule; `W → 0` becomes plain FIFO, as `W = 10` already shows). The correct response to overload is more capacity, with aging as a safeguard against indefinite waiting; a hospital would also cap the aging so that S1 is always seen immediately.

## 9. Deployment decision – can it serve 5,000 patients a day?
**Yes.** 5,000 patients/day ≈ 3.5 arrivals per minute. Admitting and treating 5,000 patients took **8.3 ms in total (≈ 1.7 µs per patient)** out of 86,400,000 ms in a day, and even a queue of 1,000,000 waiting patients costs only ≈ 0.1–0.4 µs per operation. The real queue holds at most a few hundred patients, so the data structure is nowhere near a bottleneck; the limiting resource is doctors, not the algorithm. Conditions for deployment: use the age-adjusted fair rule (or an equivalent cap), keep the display via a sorted snapshot (O(n log n) on a few hundred patients), and make `admit`/`next` thread-safe (e.g. `PriorityBlockingQueue` or external locking) if several terminals use the queue.

## 10. Conclusion
`PriorityQueue` with `(severity, arrival sequence)` meets the rule exactly, scales logarithmically, and is easy to extend to a fairness rule; strict priority starves low-severity patients, so a bounded-wait key is needed in production.
