## 1. Problem and aim
A railway e-ticket is built by joining many fields (PNR, names, coach, berth, fare, journey details). The existing code uses `+` inside a loop. The aim is to find out **whether the choice of `String`, `StringBuilder` or `StringBuffer` really matters**, and which class suits (a) the per-ticket text and (b) a log shared by several booking threads.

## 2. Prediction (made before implementation)
**Reasoning.** `String` is immutable. Every `s = s + field` creates a *new* `String` (and a new `byte[]`) and copies **all** characters collected so far. For a ticket of `n` fields of average length `L` the characters copied are `L + 2L + … + nL = L·n(n+1)/2`, i.e. **O(n²)**, and `n` intermediate `String` objects are created. `StringBuilder` keeps one growable `byte[]` and doubles it when full, so each character is copied only a constant number of times on average: **O(n)** and only `O(log n)` buffers. `StringBuffer` has the same algorithm as `StringBuilder` but every method is `synchronized`, so I expect a small constant-factor cost in a single thread and a correctness benefit under several threads.

| Workload | Prediction |
|---|---|
| W1 – short ticket (10 fields, ~98 chars) | All three close together; `+` perhaps 1.5–3× slower, but the absolute time is tiny. |
| W2 – 10,000 tickets × 50 fields (~532 chars) | `+` clearly slower (≈3–5×) and allocates many times more memory. |
| W3 – one huge ticket of 20,000 fields (~267 K chars) | Quadratic effect: `+` hundreds to thousands of times slower; `StringBuilder` ≈ `StringBuffer`. |
| Threads – shared log | `StringBuilder` will sometimes lose characters or throw; `StringBuffer` will always be exact. |

## 3. Experiment design
* **Workloads:** W1 and W2 are the two deliberately contrasting workloads from the brief; **W3 (my own)** isolates the growth of `n`.
* **Approaches:** `+` in a loop, `StringBuilder`, `StringBuffer`; plus the alternatives `String.join`, `StringJoiner`, `String.format` (Section 7).
* **Measures:** execution time with `System.nanoTime()` averaged over repeated runs (warm-ups first), bytes allocated by the thread (`ThreadMXBean.getThreadAllocatedBytes`), estimated intermediate objects per ticket (formula in the code), heap used before/after (`Runtime`).
* All approaches are first checked to produce **identical text**.

## 4. Source code
```java
import java.lang.management.ManagementFactory;
import java.util.StringJoiner;

/** Q1 - Railway e-ticket generation: String (+) vs StringBuilder vs StringBuffer (+ alternatives). */
public class Q1Ticket {
    static long sink = 0; // prevents dead-code elimination

    static String[] makeFields(int n) {
        String[] f = new String[n];
        for (int j = 0; j < n; j++) f[j] = "F" + j + "=VAL" + (j * 7919 % 1000) + "|";
        return f;
    }

    // ---------- the three required approaches ----------
    static String viaConcat(String[] f) { String s = ""; for (String x : f) s = s + x; return s; }
    static String viaBuilder(String[] f) { StringBuilder sb = new StringBuilder(); for (String x : f) sb.append(x); return sb.toString(); }
    static String viaBuffer(String[] f) { StringBuffer sb = new StringBuffer(); for (String x : f) sb.append(x); return sb.toString(); }
    // ---------- alternatives ----------
    static String viaJoin(String[] f) { return String.join("", f); }
    static String viaJoiner(String[] f) { StringJoiner j = new StringJoiner(""); for (String x : f) j.add(x); return j.toString(); }
    static String viaFormat(String[] f) { String s = ""; for (String x : f) s = String.format("%s%s", s, x); return s; }

    interface Builder { String build(String[] f); }

    static long allocated() {
        com.sun.management.ThreadMXBean b = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        return b.getThreadAllocatedBytes(Thread.currentThread().threadId());
    }

    /** returns {avg ms per full workload run, avg bytes allocated per run} */
    static double[] measure(Builder b, String[] f, int builds, int warm, int runs) {
        for (int w = 0; w < warm; w++) for (int i = 0; i < builds; i++) sink += b.build(f).length();
        double totalMs = 0; long totalAlloc = 0;
        for (int r = 0; r < runs; r++) {
            long a0 = allocated(); long t0 = System.nanoTime();
            for (int i = 0; i < builds; i++) sink += b.build(f).length();
            totalMs += (System.nanoTime() - t0) / 1e6; totalAlloc += allocated() - a0;
        }
        return new double[]{totalMs / runs, (double) totalAlloc / runs};
    }

    static long estObjectsConcat(int n) { return 2L * n; }          // String + byte[] per '+'
    static long estObjectsBuilder(int totalChars) {                   // SB + byte[] + resizes + String + byte[]
        int cap = 16, resizes = 0; while (cap < totalChars) { cap = cap * 2 + 2; resizes++; }
        return 2 + resizes + 2;
    }

    static void workload(String name, int builds, int nFields, boolean withFormat, int warm, int runs) {
        String[] f = makeFields(nFields);
        int chars = viaBuilder(f).length();
        System.out.println("\n=== " + name + ": " + builds + " ticket(s) x " + nFields + " fields (ticket length = " + chars + " chars) ===");
        // correctness: all approaches must give the same text
        boolean same = viaConcat(f).equals(viaBuilder(f)) && viaBuilder(f).equals(viaBuffer(f))
                && viaBuffer(f).equals(viaJoin(f)) && viaJoin(f).equals(viaJoiner(f));
        System.out.println("All approaches produce identical text: " + same);
        System.out.printf("%-14s %14s %16s %18s %22s%n", "Approach", "total ms/run", "us per ticket", "MB allocated/run", "est. objects/ticket");
        String[] names = {"String (+)", "StringBuilder", "StringBuffer", "String.join", "StringJoiner", "String.format"};
        Builder[] bs = {Q1Ticket::viaConcat, Q1Ticket::viaBuilder, Q1Ticket::viaBuffer, Q1Ticket::viaJoin, Q1Ticket::viaJoiner, Q1Ticket::viaFormat};
        for (int k = 0; k < bs.length; k++) {
            if (k == 5 && !withFormat) { System.out.printf("%-14s %14s %16s %18s %22s%n", names[k], "skipped", "-", "-", "-"); continue; }
            double[] m = measure(bs[k], f, builds, warm, runs);
            String est = k == 0 || k == 5 ? String.valueOf(estObjectsConcat(nFields)) : (k <= 2 ? String.valueOf(estObjectsBuilder(chars)) : "~" + estObjectsBuilder(chars));
            System.out.printf("%-14s %14.3f %16.3f %18.2f %22s%n", names[k], m[0], m[0] * 1000 / builds, m[1] / 1e6, est);
        }
    }

    // ---------- thread-safety demonstration ----------
    static void threadTest() throws Exception {
        final int T = 8, PER = 200_000;
        System.out.println("\n=== Shared log: " + T + " threads x " + PER + " appends of \"ab\" (expected length " + (T * PER * 2) + ") ===");
        for (int trial = 1; trial <= 5; trial++) {
            StringBuilder unsafe = new StringBuilder(); StringBuffer safe = new StringBuffer();
            final int[] errors = {0};
            Thread[] ts = new Thread[T];
            for (int i = 0; i < T; i++) {
                ts[i] = new Thread(() -> { for (int k = 0; k < PER; k++) { try { unsafe.append("ab"); } catch (RuntimeException e) { synchronized (errors) { errors[0]++; } } safe.append("ab"); } });
            }
            for (Thread t : ts) t.start(); for (Thread t : ts) t.join();
            System.out.printf("Trial %d: StringBuilder length=%d (lost %d, exceptions %d) | StringBuffer length=%d%n",
                    trial, unsafe.length(), T * PER * 2 - unsafe.length(), errors[0], safe.length());
        }
        // uncontended cost of synchronization
        long t0 = System.nanoTime(); StringBuilder a = new StringBuilder(); for (int i = 0; i < 20_000_000; i++) a.append('x'); double sbMs = (System.nanoTime() - t0) / 1e6;
        t0 = System.nanoTime(); StringBuffer b = new StringBuffer(); for (int i = 0; i < 20_000_000; i++) b.append('x'); double sfMs = (System.nanoTime() - t0) / 1e6;
        System.out.printf("Single thread, 20M appends: StringBuilder %.1f ms, StringBuffer %.1f ms%n", sbMs, sfMs);
        sink += a.length() + b.length();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("Name: RITHISH KUMAR D | Reg.No: 192565089 | Java " + System.getProperty("java.version"));
        Runtime rt = Runtime.getRuntime();
        System.gc(); long before = rt.totalMemory() - rt.freeMemory();
        workload("W1 short ticket", 200_000, 10, true, 3, 5);
        workload("W2 many tickets", 10_000, 50, true, 3, 5);
        workload("W3 one very long ticket", 3, 20_000, false, 1, 3);
        long afterNoGc = rt.totalMemory() - rt.freeMemory();
        System.gc(); long after = rt.totalMemory() - rt.freeMemory();
        System.out.printf("%nHeap used before: %.2f MB | after workloads (before GC): %.2f MB | after GC: %.2f MB%n", before / 1e6, afterNoGc / 1e6, after / 1e6);
        threadTest();
        System.out.println("(sink=" + (sink != 0) + ")");
    }
}
```

## 6. Measured evidence and comparison with the prediction
| Workload | Approach | µs per ticket | MB allocated per run | Ratio vs `StringBuilder` (time / memory) |
|---|---|---:|---:|---|
| W1 (10 fields) | `+` | 0.137 | 187.2 | 2.0× / 1.9× |
| | StringBuilder | 0.070 | 96.0 | 1× |
| | StringBuffer | 0.073 | 96.0 | 1.04× / 1× |
| W2 (10,000 × 50) | `+` | 0.927 | 155.0 | 2.9× / 8.6× |
| | StringBuilder | 0.318 | 18.1 | 1× |
| | StringBuffer | 0.335 | 18.1 | 1.05× / 1× |
| W3 (1 × 20,000) | `+` | 178,167 | 7,821.8 (3 builds) | ≈1,850× / ≈3,040× |
| | StringBuilder | 96 | 2.57 (3 builds) | 1× |
| | StringBuffer | 143 | 2.57 | 1.5× / 1× |

**What matched the prediction**
* The gap grows with the ticket size: 2.0× (W1) → 2.9× (W2) → ~1,850× (W3). The W3 figure is the O(n²) behaviour in action: the quadratic formula predicts `20,000 × 266,690 / 2 ≈ 2.67 GB` copied per ticket, and the measured allocation is `7,821.8 MB / 3 ≈ 2.6 GB` per ticket.
* Memory: `+` allocates 1.9×, 8.6× and ~3,000× more than `StringBuilder`.
* `StringBuilder` and `StringBuffer` are within a few percent of each other for ticket building (W1, W2) because the synchronization is uncontended and amortised over a whole ticket.

**What differed from the prediction**
* In W1 the absolute difference is only ~0.07 µs per ticket. The Java compiler turns `s + x` into a single optimised concatenation, so for a 10-field ticket the choice is **practically negligible**. The answer to "does it matter?" is therefore *it depends on `n`*: negligible for short tickets, decisive for large ones.
* A micro-test of 20 million single-character appends showed `StringBuffer` ≈ 7× slower than `StringBuilder` (493 ms vs 68 ms). The overhead of `synchronized` is real but is hidden when each call does more work (W2).
* `String.format` was far slower than I predicted: 5.13 µs vs 0.32 µs per ticket in W2 (16×) and 0.75 vs 0.07 µs in W1, because every call parses the format string and builds a `Formatter`.
* `Runtime` heap figures (1.22 MB before, 3.89 MB after the run, 2.84 MB after GC) are not useful here because the garbage is collected during the run; the **allocated-bytes counter is the reliable memory evidence**.
* Timings were taken on a 1-CPU sandbox; absolute numbers will differ on your machine but the ratios should look similar.

## 7. Design decision for the multithreaded booking server
| Use | Recommended class | Defence |
|---|---|---|
| Text of **one ticket** | `StringBuilder` | The builder is a local variable created inside the method, so it is never shared between threads. No synchronization is needed and it is the fastest (O(n), few objects). |
| **Shared booking log** appended by several threads | `StringBuffer` (or better, a thread-safe design) | In the experiment, 8 threads each appending 200,000 times to a shared `StringBuilder` lost characters in some trials (output shows trial 5: **1,253,212 of 3,200,000 characters lost**), while `StringBuffer` was exact in every trial because its methods are `synchronized`. |

Caveats I would mention in the viva: (i) the failures are timing-dependent, so some trials look correct – absence of a failure is not proof of safety; (ii) `StringBuffer` makes *each call* atomic, not a *sequence* of calls: `log.append(time).append(msg)` from two threads can interleave, so build the whole line first and append it once, or guard it with a lock; (iii) in production a shared `StringBuilder`/`StringBuffer` log would also grow without bound, so a `ConcurrentLinkedQueue<String>`, a `BlockingQueue` with a writer thread, or a logging framework is the stronger design.

## 8. Alternative concept and complexity analysis
```java
String ticket = String.join("", fields);                       // one call, exact size pre-computed
StringJoiner j = new StringJoiner(""); for (String f : fields) j.add(f);   // builder-like
String t = String.format("%s%s...", a, b);                     // convenient, slowest (parses a pattern)
```
`String.join` and `StringJoiner` are built on the same idea as `StringBuilder`: no intermediate `String` per field. `String.join` first computes the total length and allocates the result once, so it allocated the least (W2: 7.9 MB vs 18.1 MB for `StringBuilder`; W3: 1.04 MB vs 2.57 MB). `String.format` is a convenience for a *fixed, small* number of values, not for a loop.

| Approach | Time to build a ticket of `n` fields (length `L` each) | Extra space (intermediate objects) | Measured (W3 allocation, 3 builds) |
|---|---|---|---|
| Repeated `+` | Σ i·L = **O(n²·L)** chars copied | `n` intermediate `String`s (+ `byte[]`s), `O(n²·L)` bytes allocated in total, `O(n·L)` live at a time | 7,821.8 MB |
| `StringBuilder` / `StringBuffer` | **O(n·L)** amortised (doubling: each char copied ≤ ~2 times) | one buffer ≤ 2× final size + final `toString` copy ≈ 3× final length in total | 2.57 MB |
| `String.join` | **O(n·L)** (two passes: total length, then copy) | one result array (+ the element array) ≈ 1–1.5× final length | 1.04 MB |
| `StringJoiner` | O(n·L) | small internal array of strings + result | 1.59 MB |
| `String.format` in a loop | O(n²·L) plus a large constant (pattern parsing, `Formatter` object per call) | `n` intermediate `String`s + `n` `Formatter`s | not run for W3 (too slow); W2 allocated 683.8 MB vs 18.1 MB |

## 9. Conclusion
* For short tickets the choice is negligible; as the number of fields grows, repeated `+` becomes quadratic and unacceptable (≈1,850× slower for a 20,000-field ticket).
* Use `StringBuilder` (or `String.join` when the pieces are already in a collection) for the ticket text, and a thread-safe structure for the shared log: `StringBuffer` as the minimum, a queue/logging framework as the better engineering choice.
