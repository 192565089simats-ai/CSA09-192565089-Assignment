## 1. Problem and aim
A music app stores each playlist in an `ArrayList<Song>`. Users add songs at the end, insert at chosen positions, remove songs and jump to the k-th song. The aim is to find the usage pattern in which `ArrayList` is a reasonable choice, the point where I would stop recommending it, and to re-evaluate the choice when an "Up Next" queue (add at both ends, remove from the front) is introduced.

## 2. Predictions (before measuring)
| Operation | ArrayList | LinkedList | ArrayDeque |
|---|---|---|---|
| Add at end | O(1) amortised | O(1) | O(1) amortised |
| Insert / remove at **front** | O(n) – all elements shift | O(1) | O(1) |
| Insert / remove in the **middle** | O(n) – shift (fast `arraycopy`) | O(n) – **walk** to the position, then O(1) link | not supported |
| Get k-th | **O(1)** | O(n) – walk from the nearer end | not supported |
| Iterate all | O(n), best cache locality | O(n), pointer chasing | O(n) |

I predict: ArrayList wins `get(k)` and iteration by a wide margin; LinkedList and ArrayDeque win front operations; LinkedList's "O(1) insert" is a myth for a middle position because finding the position costs O(n); ArrayDeque should be the best structure for the Up-Next queue.

## 3. Experiment design
* Sizes **n = 1,000, 10,000 and 100,000** songs (boxed `Integer`).
* Each position-based test performs 1,000 operations (insert + remove pairs so the size stays `n`; `get` uses a pseudo-random `k`). Add-at-end builds the whole list; iteration is divided by `n`.
* Every figure is the **average of repeated runs after warm-up**, reported as **nanoseconds per operation**.
* A plain `int[]` with **manual shifting** is included as the alternative concept. Memory per element is measured from heap difference for 1,000,000 elements.
* Changed condition: 200,000 mixed `addLast / addFirst / removeFirst` operations on each structure (ArrayList uses `add(x)`, `add(0,x)`, `remove(0)`).

import java.util.*;

/** Q2 - ArrayList vs LinkedList vs ArrayDeque (and a manual array) for a playlist editor. */
public class Q2Playlist {
    static long sink = 0;
    interface Op { void run(); }

    /** average nanoseconds per operation, best of several repetitions' average */
    static double perOpNs(Op op, int ops, int warm, int runs) {
        for (int i = 0; i < warm; i++) op.run();
        double tot = 0;
        for (int i = 0; i < runs; i++) { long t = System.nanoTime(); op.run(); tot += System.nanoTime() - t; }
        return tot / runs / ops;
    }

    static List<Integer> fill(List<Integer> l, int n) { for (int i = 0; i < n; i++) l.add(i); return l; }

    /** plain array with manual shifting (the "alternative concept") */
    static class ManualArray {
        int[] a = new int[16]; int size = 0;
        void add(int v) { if (size == a.length) a = Arrays.copyOf(a, size * 2); a[size++] = v; }
        void insert(int idx, int v) {
            if (size == a.length) a = Arrays.copyOf(a, size * 2);
            for (int i = size; i > idx; i--) a[i] = a[i - 1];   // manual shifting
            a[idx] = v; size++;
        }
        void remove(int idx) { for (int i = idx; i < size - 1; i++) a[i] = a[i + 1]; size--; }
        int get(int i) { return a[i]; }
    }

    public static void main(String[] args) {
        System.out.println("Name: RITHISH KUMAR D | Reg.No: 192565089 | Java " + System.getProperty("java.version"));
        int[] sizes = {1_000, 10_000, 100_000};
        final int OPS = 1000;     // operations per measurement for the position-based tests
        System.out.println("\nAll times are average nanoseconds PER OPERATION (lower is better).");
        System.out.println("Position tests use " + OPS + " operations on a list that already holds n songs.\n");
        System.out.printf("%-34s %8s %12s %12s %12s %12s%n", "Operation", "n", "ArrayList", "LinkedList", "ArrayDeque", "int[] manual");

        for (int n : sizes) {
            // --- add at end (build whole list: n adds) ---
            double al = perOpNs(() -> fill(new ArrayList<>(), n), n, 20, 10);
            double ll = perOpNs(() -> fill(new LinkedList<>(), n), n, 20, 10);
            double ad = perOpNs(() -> { ArrayDeque<Integer> d = new ArrayDeque<>(); for (int i = 0; i < n; i++) d.addLast(i); }, n, 20, 10);
            double ma = perOpNs(() -> { ManualArray m = new ManualArray(); for (int i = 0; i < n; i++) m.add(i); }, n, 20, 10);
            row("Add at end", n, al, ll, ad, ma);

            List<Integer> A = fill(new ArrayList<>(), n), L = fill(new LinkedList<>(), n);
            ArrayDeque<Integer> D = new ArrayDeque<>(A);
            ManualArray M = new ManualArray(); for (int i = 0; i < n; i++) M.add(i);

            // --- insert + remove at front (size stays n) ---
            al = perOpNs(() -> { for (int i = 0; i < OPS; i++) { A.add(0, i); A.remove(0); } }, OPS * 2, 8, 7);
            ll = perOpNs(() -> { for (int i = 0; i < OPS; i++) { L.add(0, i); L.remove(0); } }, OPS * 2, 8, 7);
            ad = perOpNs(() -> { for (int i = 0; i < OPS; i++) { D.addFirst(i); D.removeFirst(); } }, OPS * 2, 8, 7);
            ma = perOpNs(() -> { for (int i = 0; i < OPS; i++) { M.insert(0, i); M.remove(0); } }, OPS * 2, 8, 7);
            row("Insert+remove at FRONT", n, al, ll, ad, ma);

            // --- insert + remove in the middle ---
            al = perOpNs(() -> { for (int i = 0; i < OPS; i++) { A.add(n / 2, i); A.remove(n / 2); } }, OPS * 2, 8, 7);
            ll = perOpNs(() -> { for (int i = 0; i < OPS; i++) { L.add(n / 2, i); L.remove(n / 2); } }, OPS * 2, 8, 7);
            ma = perOpNs(() -> { for (int i = 0; i < OPS; i++) { M.insert(n / 2, i); M.remove(n / 2); } }, OPS * 2, 8, 7);
            row("Insert+remove in MIDDLE", n, al, ll, Double.NaN, ma);

            // --- get k-th (pseudo-random k) ---
            al = perOpNs(() -> { long s = 0; Random r = new Random(1); for (int i = 0; i < OPS; i++) s += A.get(r.nextInt(n)); sink += s; }, OPS, 8, 7);
            ll = perOpNs(() -> { long s = 0; Random r = new Random(1); for (int i = 0; i < OPS; i++) s += L.get(r.nextInt(n)); sink += s; }, OPS, 8, 7);
            ma = perOpNs(() -> { long s = 0; Random r = new Random(1); for (int i = 0; i < OPS; i++) s += M.get(r.nextInt(n)); sink += s; }, OPS, 8, 7);
            row("Get k-th element", n, al, ll, Double.NaN, ma);

            // --- iterate whole list (per element) ---
            al = perOpNs(() -> { long s = 0; for (int x : A) s += x; sink += s; }, n, 20, 10);
            ll = perOpNs(() -> { long s = 0; for (int x : L) s += x; sink += s; }, n, 20, 10);
            ad = perOpNs(() -> { long s = 0; for (int x : D) s += x; sink += s; }, n, 20, 10);
            ma = perOpNs(() -> { long s = 0; for (int i = 0; i < M.size; i++) s += M.get(i); sink += s; }, n, 20, 10);
            row("Iterate whole list (per element)", n, al, ll, ad, ma);
            System.out.println();
        }

        // ------------- Changed condition: "Up Next" queue -------------
        System.out.println("=== Changed condition: 'Up Next' queue (addLast, addFirst, removeFirst), 200,000 mixed operations ===");
        System.out.printf("%-34s %8s %12s %12s %12s%n", "Structure", "n", "ArrayList", "LinkedList", "ArrayDeque");
        for (int n : sizes) {
            final int OPS2 = 200_000;
            double al = perOpNs(() -> { List<Integer> q = fill(new ArrayList<>(), n); for (int i = 0; i < OPS2 / 4; i++) { q.add(i); q.add(0, i); q.remove(0); q.remove(0); } }, OPS2, 3, 5);
            double ll = perOpNs(() -> { LinkedList<Integer> q = (LinkedList<Integer>) fill(new LinkedList<>(), n); for (int i = 0; i < OPS2 / 4; i++) { q.addLast(i); q.addFirst(i); q.removeFirst(); q.removeFirst(); } }, OPS2, 3, 5);
            double ad = perOpNs(() -> { ArrayDeque<Integer> q = new ArrayDeque<>(); for (int i = 0; i < n; i++) q.addLast(i); for (int i = 0; i < OPS2 / 4; i++) { q.addLast(i); q.addFirst(i); q.removeFirst(); q.removeFirst(); } }, OPS2, 3, 5);
            System.out.printf("%-34s %8d %12s %12s %12s%n", "ns per op (incl. initial fill)", n, f(al), f(ll), f(ad));
        }

        // ------------- memory per element (analytical + measured) -------------
        System.out.println("\n=== Memory per element (measured by heap difference for 1,000,000 Integers, boxed values shared) ===");
        memory();
        System.out.println("(sink=" + (sink != 0) + ")");
    }

    static void memory() {
        Runtime rt = Runtime.getRuntime(); int n = 1_000_000;
        Integer[] shared = new Integer[n]; for (int i = 0; i < n; i++) shared[i] = i;
        System.gc(); long b0 = used(rt); ArrayList<Integer> a = new ArrayList<>(n); for (Integer x : shared) a.add(x); System.gc(); long b1 = used(rt);
        LinkedList<Integer> l = new LinkedList<>(); for (Integer x : shared) l.add(x); System.gc(); long b2 = used(rt);
        ArrayDeque<Integer> d = new ArrayDeque<>(n + 1); for (Integer x : shared) d.add(x); System.gc(); long b3 = used(rt);
        System.out.printf("ArrayList : %.1f bytes/element%nLinkedList: %.1f bytes/element%nArrayDeque: %.1f bytes/element%n",
                (b1 - b0) / (double) n, (b2 - b1) / (double) n, (b3 - b2) / (double) n);
        sink += a.size() + l.size() + d.size() + shared.length;
    }
    static long used(Runtime rt) { return rt.totalMemory() - rt.freeMemory(); }
    static String f(double v) { return Double.isNaN(v) ? "n/a" : String.format("%.1f", v); }
    static void row(String op, int n, double a, double l, double d, double m) {
        System.out.printf("%-34s %8d %12s %12s %12s %12s%n", op, n, f(a), f(l), f(d), f(m));
    }
}

## 6. Evidence and analysis (ns per operation)
Differences at n = 1,000 are partly JIT/timer noise (this sandbox has a single CPU), so the conclusions below rely mainly on n = 10,000 and 100,000.

| Operation (n = 100,000) | ArrayList | LinkedList | ArrayDeque | `int[]` manual |
|---|---:|---:|---:|---:|
| Add at end | 7.6 | 23.4 | 5.2 | 1.2 |
| Insert + remove at **front** | 7,492 | 37.4 | 31.7 | 22,368 |
| Insert + remove in **middle** | 3,611 | 93,898 | n/a | 10,702 |
| Get k-th | 96 | 59,884 | n/a | 57 |
| Iterate (per element) | 0.6 | 3.2 | 1.1 | 0.5 |

| Growth of the cost as n grows 1,000 → 10,000 → 100,000 | ArrayList | LinkedList |
|---|---|---|
| Front insert/remove | 86 → 292 → 7,492 (grows with n) | 55 → 38 → 37 (flat) |
| Middle insert/remove | 68 → 184 → 3,611 | 896 → 8,702 → 93,898 (≈ ×10 per ×10 in n: linear) |
| Get k-th | 78 → 88 → 96 (flat) | 464 → 5,040 → 59,884 (linear) |

**Observations**
1. `get(k)` is where `ArrayList` is unbeatable: ~96 ns at every size, whereas `LinkedList` becomes ~620× slower at 100,000 songs.
2. Front insert/remove is linear for `ArrayList` (7.5 µs per operation at 100,000) but constant for `LinkedList` and `ArrayDeque` (~32–37 ns) – about 200× difference.
3. For the **middle**, `LinkedList` is *not* better: it is ~26× slower than `ArrayList` at 100,000 because it must walk ~n/4 nodes on average, whereas `ArrayList` shifts references with a very fast `System.arraycopy`.
4. A hand-written shifting loop is the same Big-O as `ArrayList` but ~3× slower in practice (22,368 vs 7,492 ns at the front) because `ArrayList` uses the intrinsic `arraycopy`; it also forces me to manage resizing myself.
5. Iterating `ArrayList` is the cheapest (contiguous memory); linked nodes are scattered, so every step is a potential cache miss.
6. Memory per element (measured): `ArrayList` 4.0 B, `ArrayDeque` 4.0 B, `LinkedList` **24.0 B** (node header + item + prev + next).

## 7. Answer: operating boundary of `ArrayList`
**`ArrayList` is a reasonable engineering choice when** the playlist is read by position and appended to far more often than it is edited at the front or middle – e.g. a user's playlist of up to a few thousand songs. At n = 1,000–10,000 even a front insert costs only ~0.1–0.3 µs, which is invisible next to a UI action, and `get(k)`, iteration and memory are optimal.

**I would stop recommending it when** front or middle insertions/removals become the dominant operation **and** the list is large: the measured cost grows linearly (≈ 3.6 µs in the middle and 7.5 µs at the front for 100,000 songs) and a burst of thousands of such edits per second would saturate the CPU. At that point the data should be restructured (e.g. a deque for the queue part, or a design that avoids shifting) rather than tuned. I would **never** choose `LinkedList` for the playlist: it loses on `get(k)`, iteration, middle edits and memory, and wins only on front edits, where `ArrayDeque` is better still.

## 8. Changed condition – the "Up Next" queue
Songs are added at both ends and removed from the front: that is exactly the deque interface. Measured for 200,000 mixed operations:

| n songs in queue | ArrayList | LinkedList | ArrayDeque |
|---|---:|---:|---:|
| 1,000 | 35.1 | 13.5 | 9.8 |
| 10,000 | 197.4 | 15.2 | 7.8 |
| 100,000 | 5,876.9 | 13.8 | **4.3** |

`ArrayList` degrades linearly (≈ 1,350× slower than `ArrayDeque` at 100,000), whereas `ArrayDeque` stays at a few nanoseconds per operation with 4 B/element instead of `LinkedList`'s 24 B. **Re-evaluated recommendation:** keep `ArrayList<Song>` for the playlist itself (index access, occasional insertion) and use `ArrayDeque<Song>` for "Up Next". `ArrayDeque` is more appropriate because it has O(1) operations at both ends, no per-node allocation and good locality; its limits are that it has no index access/middle insert and does not allow `null`, which is acceptable for a queue.

## 9. Alternative concept and complexity analysis
| Operation | ArrayList | LinkedList | ArrayDeque | Plain array, manual shifting |
|---|---|---|---|---|
| Add at end | O(1) amortised (O(n) on resize) | O(1) | O(1) amortised | O(1) amortised if I implement doubling, else O(n) |
| Insert at front | O(n) | O(1) | O(1) | O(n) (hand loop, ~3× slower constant) |
| Insert in middle | O(n) shift | O(n) walk + O(1) link | not supported | O(n) |
| Get k-th | O(1) | O(n) | not supported | O(1) |
| Iterate | O(n) | O(n) (slower constant) | O(n) | O(n) |
| Space per element | 4 B slot (+ up to ~50 % spare capacity) | 24 B node | 4 B slot (+ spare capacity) | 4 B slot, fixed capacity or manual doubling |

A plain array with manual shifting gives the same complexity as `ArrayList` (it *is* what `ArrayList` does internally) but without the tuned `arraycopy`, bounds checks, `Iterator`/`modCount` safety and generics, so it is not recommended except for primitive data where boxing must be avoided.

## 10. Conclusion
`ArrayList` is a sound default for index-based, append-heavy playlists up to thousands of songs; its boundary is large lists with frequent front/middle edits. For queue-like behaviour at both ends, `ArrayDeque` is clearly the right structure, and `LinkedList` is rarely the best answer to any of these requirements.
