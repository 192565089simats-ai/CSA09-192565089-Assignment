## 1. Problem and requirements
Stock is looked up by medicine code hundreds of times a day. Every evening the system must print (R1) a report of all medicines **in code order** and (R2) a list of medicines **in the order they were added**. I compare `HashMap`, `TreeMap` and `LinkedHashMap` (plus `Hashtable` and a sorted array with `Arrays.binarySearch()` as alternatives).

## 2. Design reasoning before implementation
Design: `Map<String, Medicine>` keyed by the medicine code (`"MED0000013"` – fixed width and zero-padded, so alphabetical order equals numeric order). The `Medicine` object holds code, name and stock.

| Map | `put` | `get` | Iteration | Order of iteration |
|---|---|---|---|---|
| `HashMap` | O(1) average | O(1) average | O(n + capacity) | none (hash order) |
| `TreeMap` (red-black tree) | O(log n) | O(log n) | O(n) | **sorted by key** |
| `LinkedHashMap` | O(1) average | O(1) average | O(n) | **insertion order** |
| `Hashtable` | O(1), synchronized | O(1), synchronized | O(n) | none |

* **R1 (code order)** is produced naturally by `TreeMap`. For `HashMap`/`LinkedHashMap` extra work is needed: copy all keys and sort them, O(n log n) for every report.
* **R2 (added order)** is produced naturally by `LinkedHashMap`. For `HashMap`/`TreeMap` the "wrong map" needs an extra `List<String>` of codes in insertion order (O(n) extra memory) and one lookup per code (O(n) for `HashMap`, O(n log n) for `TreeMap`).
* Prediction: lookups – `HashMap` ≈ `LinkedHashMap` ≪ `TreeMap` (log n tree walk with cache misses); the sort step makes R1 on a hash-based map clearly slower than on `TreeMap`.

## 3. Test design
Sizes **1,000, 10,000 and 100,000** medicines (codes inserted in shuffled order so that insertion order ≠ code order). Each figure is the average of 7 runs after 3 warm-up runs; lookups = 100,000 random existing codes. For every map the program checks whether each report's **order matches the requirement** (`YES`/`NO`).

## 4. Source code
```java
import java.util.*;

/** Q4 - Hospital pharmacy: HashMap vs TreeMap vs LinkedHashMap (+ Hashtable and sorted-array/binarySearch). */
public class Q4Pharmacy {
    static long sink = 0;
    static class Medicine {
        final String code; final String name; int stock;
        Medicine(String c, String n, int s) { code = c; name = n; stock = s; }
        @Override public String toString() { return code + ":" + stock; }
    }
    static final Comparator<Medicine> BY_CODE = Comparator.comparing(m -> m.code);

    /** ------- alternative: sorted array + Arrays.binarySearch ------- */
    static class SortedArrayInventory {
        Medicine[] a = new Medicine[16]; int size = 0;
        void add(Medicine m) {
            int i = Arrays.binarySearch(a, 0, size, m, BY_CODE);
            if (i >= 0) { a[i] = m; return; }
            i = -i - 1;
            if (size == a.length) a = Arrays.copyOf(a, size * 2);
            System.arraycopy(a, i, a, i + 1, size - i); a[i] = m; size++;
        }
        Medicine get(String code) { int i = Arrays.binarySearch(a, 0, size, new Medicine(code, "", 0), BY_CODE); return i >= 0 ? a[i] : null; }
    }

    static String[] makeCodes(int n, long seed) {      // distinct, shuffled (insertion order != code order)
        List<Integer> v = new ArrayList<>(); for (int i = 0; i < n; i++) v.add(i * 7 + 13);
        Collections.shuffle(v, new Random(seed));
        String[] c = new String[n]; for (int i = 0; i < n; i++) c[i] = String.format("MED%07d", v.get(i));
        return c;
    }

    static double ms(long ns) { return ns / 1e6; }

    public static void main(String[] args) {
        System.out.println("Name: RITHISH KUMAR D | Reg.No: 192565089 | Java " + System.getProperty("java.version"));
        int[] sizes = {1_000, 10_000, 100_000};
        final int LOOKUPS = 100_000, WARM = 3, RUNS = 7;
        System.out.println("Each figure = average of " + RUNS + " runs after " + WARM + " warm-up runs. Lookups = " + LOOKUPS + " random existing codes.\n");

        for (int n : sizes) {
            String[] codes = makeCodes(n, 42);
            String[] sortedCodes = codes.clone(); Arrays.sort(sortedCodes);
            String[] probe = new String[LOOKUPS]; Random r = new Random(5); for (int i = 0; i < LOOKUPS; i++) probe[i] = codes[r.nextInt(n)];
            Medicine[] meds = new Medicine[n]; for (int i = 0; i < n; i++) meds[i] = new Medicine(codes[i], "Med" + i, 10 + i % 90);

            String[] names = {"HashMap", "TreeMap", "LinkedHashMap", "Hashtable", "SortedArray+binSearch"};
            double[] put = new double[5], look = new double[5], repCode = new double[5], repIns = new double[5], repInsExtra = new double[5];
            boolean[] codeOK = new boolean[5], insOK = new boolean[5];

            for (int run = -WARM; run < RUNS; run++) {
                // ---- build + lookup + reports ----
                @SuppressWarnings("unchecked") Map<String, Medicine>[] maps = new Map[]{new HashMap<>(), new TreeMap<>(), new LinkedHashMap<>(), new Hashtable<>()};
                for (int k = 0; k < 4; k++) {
                    Map<String, Medicine> m = maps[k];
                    long t0 = System.nanoTime(); for (Medicine x : meds) m.put(x.code, x); long t1 = System.nanoTime();
                    long s = 0; for (String p : probe) s += m.get(p).stock; long t2 = System.nanoTime(); sink += s;

                    // report 1: all medicines in CODE order
                    long t3 = System.nanoTime(); List<String> rep1 = new ArrayList<>(m.size());
                    if (k == 1) { for (String key : m.keySet()) rep1.add(key); }               // TreeMap: already sorted
                    else { for (String key : m.keySet()) rep1.add(key); Collections.sort(rep1); }   // others: extra sort needed
                    long t4 = System.nanoTime();
                    // report 2: in the order ADDED
                    List<String> rep2 = new ArrayList<>(m.size()); for (String key : m.keySet()) rep2.add(key); long t5 = System.nanoTime();
                    // the "extra work" for the wrong map: keep a side list of codes in insertion order and look each one up
                    List<String> side = Arrays.asList(codes); List<Medicine> rep2b = new ArrayList<>(n); for (String c : side) rep2b.add(m.get(c)); long t6 = System.nanoTime();

                    if (run >= 0) { put[k] += ms(t1 - t0); look[k] += ms(t2 - t1); repCode[k] += ms(t4 - t3); repIns[k] += ms(t5 - t4); repInsExtra[k] += ms(t6 - t5); }
                    codeOK[k] = rep1.equals(Arrays.asList(sortedCodes));
                    insOK[k] = rep2.equals(Arrays.asList(codes));
                    sink += rep1.size() + rep2.size() + rep2b.size();
                }
                // ---- sorted array alternative ----
                SortedArrayInventory sa = new SortedArrayInventory();
                long t0 = System.nanoTime(); for (Medicine x : meds) sa.add(x); long t1 = System.nanoTime();
                long s = 0; for (String p : probe) s += sa.get(p).stock; long t2 = System.nanoTime(); sink += s;
                long t3 = System.nanoTime(); List<String> rep1 = new ArrayList<>(n); for (int i = 0; i < sa.size; i++) rep1.add(sa.a[i].code); long t4 = System.nanoTime();
                if (run >= 0) { put[4] += ms(t1 - t0); look[4] += ms(t2 - t1); repCode[4] += ms(t4 - t3); }
                codeOK[4] = rep1.equals(Arrays.asList(sortedCodes)); insOK[4] = false;
            }

            System.out.println("=== n = " + n + " medicines ===");
            System.out.printf("%-22s %10s %12s %10s %14s %12s %12s %14s%n", "Structure", "put all ms", "100k get ms", "ns/get", "code-rpt ms", "code order?", "added-rpt ms", "added order?");
            for (int k = 0; k < 5; k++) {
                String ins = k == 4 ? "-" : String.format("%.3f", repIns[k] / RUNS);
                System.out.printf("%-22s %10.2f %12.2f %10.0f %14.3f %12s %12s %14s%n", names[k], put[k] / RUNS, look[k] / RUNS, look[k] / RUNS * 1e6 / LOOKUPS,
                        repCode[k] / RUNS, codeOK[k] ? "YES" : "NO", ins, k == 4 ? "-" : (insOK[k] ? "YES" : "NO"));
            }
            System.out.printf("Extra work for 'added order' report with side-list + lookups: HashMap %.3f ms, TreeMap %.3f ms (LinkedHashMap needs none: %.3f ms)%n%n",
                    repInsExtra[0] / RUNS, repInsExtra[1] / RUNS, repIns[2] / RUNS);
        }
        System.out.println("Note: the code-order report time for HashMap, LinkedHashMap and Hashtable INCLUDES the extra Collections.sort() step; TreeMap and the sorted array iterate directly.");
        System.out.println("(sink=" + (sink != 0) + ")");
    }
}
```

Extra work to obtain R2 from the "wrong" map (side list + one lookup per code): `HashMap` 2.57 ms, `TreeMap` **60.74 ms** (n log n lookups); `LinkedHashMap` needs none (2.17 ms).

Behaviour at the other sizes (from the output): `HashMap` lookups stay between 13 and 37 ns/get; `TreeMap` rises from 281 (1,000) → 343 (10,000) → 559 ns/get (100,000); the extra sort for R1 on a hash-based map grows from ≈ 0.3–1.1 ms (n = 1,000) → 3.8–5.5 ms (10,000) → 27–37 ms (100,000).

**Prediction vs observation.** Confirmed: `HashMap`/`LinkedHashMap` lookups are ~13–16× faster than `TreeMap` at 100,000; `TreeMap` is the only one that gives R1 without sorting; `LinkedHashMap` is the only one that gives R2 for free; every order requirement was verified by the program (`YES`/`NO` columns). A small surprise: `LinkedHashMap` was slower than `HashMap` on `put` (23 vs 9 ms) because it maintains an extra doubly-linked list, and its code-order report (37 ms) was a little slower than `HashMap`'s (28 ms) even though both sort the same keys, so I treat that gap as measurement noise rather than a real effect; the numbers at n = 1,000 are within JIT noise.

## 7. Scalability inquiry
**Acceptable response time.** For an interactive lookup by a pharmacist I define *acceptable* as **≤ 1 ms per lookup** (far below human perception) and *desirable* as **≤ 10 µs**, so that 100,000 lookups finish in about a second. Reports are an evening batch, so **≤ 1 s** per report is acceptable.

**Result.** Every structure meets the lookup criterion by a wide margin: the slowest, the sorted array / `TreeMap`, needs 0.56–0.62 µs per lookup at 100,000 medicines, i.e. ~1,800× below the limit; `HashMap`/`LinkedHashMap` need 34–43 ns. Even the "wrong-map" reports (≈ 28–37 ms for the sort) are ≈ 30× below the 1 s limit. The decision therefore rests on *which requirement dominates*, not on feasibility.

**Deployment choice: `LinkedHashMap<String, Medicine>`.** It keeps the hot operation (lookup, hundreds per day) at ≈ 43 ns, gives R2 for free, and R1 costs one sort of the keys per evening (≈ 37 ms at 100,000 medicines). If the code-order report were requested very often, or the code list had to be browsed in order interactively, I would choose `TreeMap` instead (R1 = 4.3 ms, lookups 0.56 µs – still acceptable) and pay the extra work for R2.

**Where the remaining cost comes from.** For `LinkedHashMap`: the O(n log n) sort of 100,000 strings (about 17 string comparisons per element plus cache-unfriendly node access) and, for puts, maintaining the linked list (23 ms vs 9 ms). For `TreeMap`: the O(log n) pointer-chasing per lookup/put (cache misses) and a larger entry (~40 B vs ~32 B).

**Why `Hashtable` is not preferred in new code.** It is a legacy class (Java 1.0) whose every method is `synchronized`, so it takes a lock even for single-threaded code and serialises all threads (measured 54 ns vs 34 ns per get and 21 vs 9 ms for 100,000 puts, even without contention); it forbids `null` keys/values; its enumerations are not fail-fast; and it offers no ordering. Modern alternatives are `HashMap` (single thread), `ConcurrentHashMap` (concurrent use, fine-grained locking) or `Collections.synchronizedMap` where a wrapper is acceptable.

## 8. Alternative concept: sorted array + `Arrays.binarySearch()`
```java
Medicine[] a;  int size;                                   // kept sorted by code
int i = Arrays.binarySearch(a, 0, size, key, BY_CODE);     // lookup O(log n)
// insert: i = -i - 1; System.arraycopy(a, i, a, i + 1, size - i); a[i] = m;   // O(n) shift
```
| Operation | Sorted array | HashMap | TreeMap |
|---|---|---|---|
| Lookup | O(log n) – 620 ns measured | O(1) avg – 34 ns | O(log n) – 559 ns |
| Insert | **O(n)** shift – 260 ms to insert 100,000 one at a time (≈ 30× slower than `HashMap`, ≈ 5× than `TreeMap`); if the data is loaded once, one `Arrays.sort` is O(n log n) | O(1) avg – 8.7 ms | O(log n) – 54.6 ms |
| Code-order report | **O(n)**, no sort – 0.70 ms | O(n log n) sort | O(n) – 4.3 ms |
| Space | **n references (4 B each)** + the objects, no node overhead | ~32 B node + table slot per entry | ~40 B node per entry |

The array is the most compact and gives the fastest R1, but it is unsuitable if medicines are added continually (O(n) per insertion) and its lookup is 18× slower than `HashMap`. It would only be competitive for a nearly static catalogue.

## 9. Conclusion
Match the structure to the dominant requirement: hash for lookup speed, tree for sorted traversal, linked hash for insertion order. For this pharmacy, `LinkedHashMap` meets all requirements within the acceptability criterion with the least total work, and the evening code-order sort is the remaining cost – which Q7 attacks with a redesign.
